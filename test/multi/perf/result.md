## Takeaways

- **Writes collapse above ~8 concurrent writers because the leader flaps.** With 5 nodes, write throughput stays at ~80/s for 1-8 conns, then drops to 41 → 9 → 1 writes/s at 16 / 32 / 64 conns, with hundreds of NotLeader redirects per run. Nothing errors out; the cluster spends its time re-electing. This is the #1 issue. The likely cause (not yet verified) is that heartbeats or the follower's election-timer reset sit behind batch fsyncs that take longer than the 150 ms election timeout under load. The 80 ms `replication.rpc.attempt.timeout.ms` is also tight for an fsync'd batch.
- **Scaling (16 conns): 1 → 3 → 5 nodes = 265 → 88 → 27 writes/s.** Part of that is the expected quorum fsync cost, but most of the 5-node drop is the flapping above. Below the flapping point (8 conns) a 5-node write costs ~110 ms p50, vs ~5 ms for a single-node write at 1 conn.
- **Reads don't depend on cluster size** (~155k/s at 16 conns for n = 1, 3, 5) and keep scaling with concurrency (68k → 206k/s, p99 ≤ 1 ms) because `read.from=any` serves them locally. These reads can be stale on followers.
- **Mixed load is capped by writes.** At 90/10, reads hit 6.7k/s but writes manage only 3/s, because each connection's next read waits behind a write stuck in an election.
- **Slow followers: the expected "1-2 slow is free" result is not visible yet.** With +20 ms RTT on 1, 2 or 3 followers, p50 stays ~105-130 ms, and p99 rises with the number of slow links (133 → 192 ms). Elections still happen during these runs, so the numbers are noisy. Rerun this once flapping is fixed.
- **Caveat:** all 5 nodes share one laptop SSD and 10 CPUs, so fsyncs contend. On real separate machines, writes/s per cluster should be closer to single-node numbers.
