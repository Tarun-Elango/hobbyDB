## Takeaways

- **Safety holds:** 0 acked writes lost in every case. With 3 of 5 down nothing was acked, and survivors still served stale-but-committed reads (`v1`).
- **Availability with 2 down:** writes keep working with 1 or 2 nodes down, either followers or the leader. Writes/s actually go *up* with fewer nodes (80 → 97) because all 5 nodes share one laptop disk, so fewer fsyncs compete. On separate machines expect flat or slightly lower numbers.
- **Leader failover ≈ 300 ms** of zero writes (election timeout 150-300 ms plus redirect). Each of the 8 clients sees one connection error when the leader dies and then finds the new leader by itself.
- **Leader without a quorum keeps acting as leader.** Followers redirect clients to it and every write hangs for the full 5 s propose timeout instead of failing fast. Adding a check-quorum step-down to Raft would turn this into an immediate NotLeader.
- **A timed-out write isn't a failed write.** The `v2` that timed out on the isolated leader committed once a node came back (`q after = v2`). Clients must treat a commit timeout as "unknown" and retry with the same ClientID/Seq so it's applied once.
- **Cluster write throughput is ~2.5x lower than a single node** (~80 vs ~200 writes/s at similar concurrency), because each write waits for a quorum of fsyncs.
